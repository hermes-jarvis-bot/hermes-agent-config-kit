# Security policy

## Trust model

Upstream content from `AnastasiyaW/claude-code-config` is treated as data, not as executable authority.

This adapter may snapshot, classify, and transform selected markdown artefacts into Hermes-compatible skills. It must not automatically execute upstream hooks, scripts, workflows, plugin descriptors, or shell snippets.

## Safety guarantees for the MVP

- No automatic writes to `~/.hermes`.
- No automatic Hermes gateway start or restart.
- No automatic execution of upstream hooks or scripts.
- No automatic installation of upstream plugin metadata.
- No use of production credentials in CI.
- No auto-merge of upstream changes: sync workflows create draft PRs, and only an
  operator may move a sync PR to review, approve it, or merge it.
- Upstream sync is batched into reviewable changes rather than applied directly to a live agent.

## Quarantine lane

The following upstream artefacts are manual-review only:

- `hooks/**`
- `scripts/**`
- `.claude-plugin/**`
- `.github/workflows/**`
- files that appear to handle credentials, shell execution, deletion, network calls, or process control

Quarantined files may be included in the upstream snapshot for review, but they are not installed into Hermes by the MVP installer.

## Reviewed-script lane

A narrow, explicitly-allowlisted exception to the quarantine lane exists for **skill-bundled**
scripts — a script that ships inside a generated skill's own `scripts/` subfolder and is invoked
by the operator or agent at runtime, the same way Hermes's own official skills (`xlsx`, `pdf`,
`linear`) ship and invoke their bundled scripts. This is not the same thing as a Claude-Code
`hooks/**` file: a hook has a harness-lifecycle I/O contract (stdin JSON, exit codes) that Hermes
has no equivalent for, and stays fully quarantined.

A script may exist under `hermes/skills/**/scripts/` only if every one of these has been done, in
order, by a human (or an agent acting under explicit human authorisation for this exact script):

1. Read the entire script by hand — not a grep-only pass.
2. Check its dependencies — prefer stdlib; document any external dependency as an explicit
   prerequisite, the same way this repo documents installer prerequisites elsewhere.
3. Confirm it performs no destructive filesystem operation, reads or logs no credential/secret,
   and makes no undisclosed network call.
4. Check path portability — no hardcoded Claude-Code-specific paths (`.claude/`, `~/.claude/`)
   unless deliberately kept as documented upstream-source context.
5. Confirm it passes a syntax check (`compile()`/`py_compile` for Python, the JS/TS equivalent
   for JS).
6. Confirm it passes this repo's automated dangerous-pattern and secret scans
   (`validate_reviewed_scripts()` in `scripts/validate_output.py`) — checked for `os.system`,
   `shell=True` subprocess calls, `eval`/`exec`, raw socket creation, and credential-looking
   patterns.
7. Confirm it is never invoked automatically by this adapter or its CI — only ever by an
   operator or agent at runtime, under Hermes's own normal permission/consent system.

The allowlist lives in `mappings/reviewed-scripts.yaml`, one entry per script, recording the
`source_sha256` of the exact upstream fetch that was reviewed, who reviewed it and when, a
one-paragraph summary of what the review found, and any live functional-test evidence. A script
here is never auto-converted or auto-regenerated by `scripts/sync_upstream.py`'s
`SUPPORTED`/`convert_supported()` fast lane — that pipeline is markdown-only. If the upstream
source later changes (its live SHA-256 no longer matches `source_sha256`), the change must be
re-reviewed by hand against the same 7 steps before the manifest entry is updated.

## Reporting a vulnerability

Open a private report with the maintainer, or contact the operator through the agreed operational channel. Do not include secrets in issue bodies, PR descriptions, logs, or screenshots.

If a credential appears in repository content, rotate it first and then remove it from history. Treat exposure as real until proven otherwise.

## Review checklist for upstream sync PRs

Before merging a sync PR:

- inspect the upstream commit range;
- review the generated report under `reports/upstream-sync/`;
- confirm generated Hermes skills are markdown-only and have valid frontmatter;
- confirm quarantine counts and paths make sense;
- if a new reviewed script was added, confirm `mappings/reviewed-scripts.yaml` records its
  `source_sha256`, reviewer, and review date, and that the 7-step gate above was actually followed;
- check that no generated skill instructs live profile writes without operator confirmation;
- run `python3 scripts/validate_output.py`;
- run installer dry-run against a temp path;
- do not run `--apply` outside a disposable Hermes home.
